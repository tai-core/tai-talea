# 容器内准备与制品设计（讨论稿）

> 回答三个问题：push/pull 的定位、镜像与代码包怎么放、不能自定义镜像时依赖怎么管。
> 日期：2026-09-17 起草，2026-09-18 增补 §7（自动化铺装机制，含实测数据）。

## 0. 结论速览

| 问题 | 结论 |
| --- | --- |
| push 与 pull 是否都要 | **都要**，且两者是**平级的发现通道**，都不涉及申请容量 |
| 这两条通道现在的状态 | Pull 已完整实现，默认关闭；打开是一行配置。唯一缺口在"合作商直接 push 全量快照"那条路 |
| 容器启动后动态拉代码包 | **开发文档里已经有**，叫「签名业务包」，排在 M3。需要提前并具体化 |
| 镜像放 GitHub 吗 | GitHub 放**源码与 Dockerfile**；**镜像是构建产物，要推到 OCI 镜像仓库**。两者不是一回事 |
| 不能自定义镜像时怎么管依赖 | 优先级：共享环境目录 > 预打包 venv 制品 > 运行时 pip install |
| 合作商**只给最基础镜像**（如 ubuntu22.04/cu12.8/py3.10）时，能否把依赖全自动装齐 | **能**，且不需要镜像能力也不需要 docker。机制是**种子 + 清单 + 载体**三层可分离结构，见 §7 |

## 1. push 与 pull：两条并行的发现通道

**先把语义钉死**（这一点文档现在的措辞有误导）：

- push 与 pull **都只是"获取闲置容量信息"的通道**——一个是对面推给我们，一个是我们去问对面。
- **两者都不涉及"申请/创建容量"**。闲置容量是对面给的，我们只做发现、接管、归还。
  这与 §11「不主动制造合作商新容量需求」一致，也被平台现实印证：
  **九章智算云根本没有"创建实例"的 API**，创建只能在控制台。

**因此文档 §6.2 的措辞建议修订。** 现在写的是：

> Pull 对账结果是容量权威来源，Push 只作为实时加速器。

这句话读起来像 Push 是二等公民、且隐含了"申请"语义。更准确的表述是：

> Push 与 Pull 是两条**等价**的容量发现通道。Pull 天然提供全量快照，因此**承担对账与纠偏职责**；
> Push 提供实时性。两者互为兜底：Push 丢失由下一次 Pull 补上，Pull 不可用时 Push 仍能工作。

**现状核对（实测代码，不是推测）**：

| 通道 | 状态 |
| --- | --- |
| Push | 已实现。`POST /v1/capacity/events`，合作商级认证 + HMAC + 时间戳窗口 + `event_id` 幂等 |
| Pull | **已完整实现并有测试，默认 `pull.enabled: false`**。`internal/partner/pull.go` 按 §6.2 生成 `CAPACITY_ADDED` / `CAPACITY_UPDATED` / `CAPACITY_REVOKED`；**无变化时**才发一条 `CAPACITY_SNAPSHOT_CONFIRMED` 作为"什么都没变"的权威声明。失败时保留上次成功快照、不误判撤销、发 `PARTNER_SYNC_FAILED` 告警 |
| Pull 的"权威来源"语义 | 排在 M2。要启用只需打开开关并走完语义确认 |

**唯一真实缺口**：如果合作商选择**直接 push 一份全量快照**（`CAPACITY_SNAPSHOT_CONFIRMED`），
那么"与上一次快照 diff 并生成 REVOKED"这一步就没人做了——
`handleSnapshotConfirmed` 目前只写审计 + 漂移告警，**不会真的回收**快照里缺失的实例。
保守是有道理的（§6.2 要求"不得把全部实例误判为撤销"），但既然要支持 push 快照，
就得补上"与本地已跟踪实例做 diff 并回收"的动作。

## 2. 两个制品，务必分开

这是当前讨论里最容易混的一处。**镜像和代码包是两个独立制品，走两条独立的版本线。**

| | 运行时基底镜像 | 部署代码包 |
| --- | --- | --- |
| 装什么 | OS / CUDA / Python / 依赖（torch、sglang…）/ 极小的引导程序 | tai-core 的业务代码 |
| 变更频率 | 低（CUDA、SGLang 大版本变才动） | 高（每次发版） |
| 版本号 | 镜像 tag，tag 对应一个构建 commit | git tag/commit + 内容 digest |
| 存放位置 | **OCI 容器镜像仓库**（九章平台私有镜像 / ghcr.io / 自建 Harbor） | 我们的控制节点或制品库 |
| 谁拉 | 平台在创建实例时拉 | 容器启动后自己拉 |

**关于"镜像放在 GitHub 上、容器去拉对应 commit"——需要拆成三件事：**

1. **GitHub 仓库**放**源码和 Dockerfile**（可复现），必要时用 GitHub Actions 构建。
2. **构建产物（镜像）推到 OCI registry**。GitHub 的对应物是 **ghcr.io**，不是仓库本身。
   "把镜像放在 GitHub 上"严格说是"把镜像推到 ghcr.io"。
3. **"容器去拉 commit"这个说法不准确。** 容器拉的是**构建产物**（镜像 tag 或代码包 digest），
   产物与 commit 之间靠 tag/label 建立映射。直接 `git clone` 某个 commit 技术上可行
   （实测容器内有 git 2.34.1），但生产上更推荐拉**不可变 tarball + 校验 digest**，
   避免 git 依赖和分支漂移。

## 3. 容器启动后动态拉取代码包

**这个需求开发文档里已经写了**，在 §10「后续：可自定义镜像路线」里，名字叫**签名业务包**：

```
• 下载签名业务包。
• SHA256 校验。
• ed25519 签名校验。
• 原子解压。
• drain 后升级。
• 失败回滚到旧版本。
• 旧版本和新版本并存一段时间。
```

§15 安全要求也已写明「业务包必须校验 SHA256 和签名」，§17 把它排在 M3。
**所以这不是新增设计，而是把 M3 的一项提前并具体化。**

**落地需要的零件**（按依赖顺序）：

| 需要什么 | 现状 |
| --- | --- |
| 容器能出站到我们的控制节点 | ✅ 实测容器可出公网（`codeload.github.com` 拉 tarball HTTP 200、`baidu.com` 200） |
| 引导凭据（容器怎么证明自己是我们授权的） | ⚠️ 部分具备。已有 `X-Bootstrap-Token` 共享密钥机制，可复用或扩展为按实例下发 |
| 完整性校验 | ❌ 未实现。§15 已要求 SHA256 + ed25519 |
| 版本选择（拉哪个版本由谁定） | ❌ 未实现。建议容器上报自己的 profile，控制面决定版本 |
| 原子解压与 drain 后升级 | ❌ 未实现，§10 已列 |
| 失败回滚、新旧并存 | ❌ 未实现，§10 已列 |

### ⚠️ 必须说清的一点：它降低的是"镜像层"暴露，不是"运行期"暴露

"代码不泄露到镜像里"这个目标，运行时拉取能做到的是：

- ✅ 镜像仓库里**不含**我们的代码，镜像本身可以被合作商查看、复用、分发而不带我们的代码；
- ✅ 暴露窗口可控：凭据可吊销、版本可轮换、不同合作商给不同版本；
- ✅ 镜像可以随时重新构建，不必担心历史镜像里躺着旧代码。

但**不能**做到：

- ❌ 运行期对平台不可见。合作商运行这台容器、对它持有 root，
  **代码一旦落到容器的文件系统，平台上就是可读的**。

如果目标里包含"运行期也不让对方看到源码"，那需要别的手段（发布编译产物而非源码、
把敏感逻辑留在我们侧不让它进容器、或约定信任边界），运行时拉取解决不了这个问题。
**建议先明确这一点，否则容易在错误的机制上投入。**

## 4. 依赖管理：不能自定义镜像时怎么办

实测数据支撑下面的排序：容器内 `pip install sglang==0.5.19` 要从清华源拉
`torch-2.13.0` 等轮子，**实测带宽约 128KB/s**，1GB 级轮子需要两个多小时。
按"资源可能会比较多"的预期，这个方式无法规模化。

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **① 共享环境目录** | 用九章支持的 NAS 挂载，把**预先构建好的 venv 挂在每个容器里的同一绝对路径**下 | **规模化最优**。构建一次、所有容器共用，容器启动零安装。前提是 NAS 可多实例共享且挂载路径一致（**待确认**） |
| **② 预打包 venv 制品** | 在我们这边构建好 venv（或 wheelhouse），打包成 tar.zst 放制品库，容器启动后拉取并原子解压 | 快、可复现、可校验 digest。比 pip 逐包解析稳得多。适合无共享存储时 |
| **③ 运行时 pip install** | 容器启动后 `pip install -r requirements.txt` | 九章官方教程的做法（`pip install vllm`），零准备成本，但**慢且不稳定**，不适合规模化。可作兜底 |

注意系统盘只有 **49GB**，而 sglang + torch 的 venv 体积在 GB 级。
每个容器各装一份既费时又费盘；**方案 ① 把这份开销变成全局一份**，是规模化下的自然选择。

## 5. 规模化带来的另外两个硬约束

1. **SSH 必须用密钥，不能每台给密码。** 现在这台是密码登录，纯手工。
   九章支持**公钥预注入**（登记一次，之后创建的实例自动注入当前列表内所有公钥），
   这是自动化的前提，必须在规模化之前落实。
2. **不能依赖 `save-image` 做主要分发**。它适合做一次性的基线固化，
   但代码包变更频繁、且镜像体积大（GB 级），用镜像做代码分发会导致每次发版都重建镜像。

## 7. 自动化铺装：在任意基础镜像上把依赖装齐（2026-09-18 实测）

> 问题：合作商只给最基础的镜像（如 ubuntu 22.04 / cuda 12.8 / python 3.10），
> 我们能不能把这些之外**所有需要的依赖**通过某种方式全部自动装好？

### 7.1 结论

**能，而且不需要镜像能力、不需要 docker、不需要平台配合。** §4 给的是"三个方案排序"，
没回答机制；机制是**三个可分离的部件**：

| 部件 | 是什么 | 换合作商要改吗 |
| --- | --- | --- |
| **种子 seed** | 纯标准库 Python 单文件（几十 KB），零第三方依赖。只做编排：探测环境 → 取清单 → 装配 → 自检 → 交棒 | 不改 |
| **清单 manifest** | 声明"装什么、装哪个版本"：兼容类 + apt 包 + pip 锁 + 我们的组件（按 digest 钉死） | 只新增一个兼容类 |
| **载体 carrier** | "怎么把载荷送进容器"：共享存储 / 派生镜像 / SSH / 启动脚本 / 公网镜像源 | 每合作商一个实现 |

关系是：**种子是引擎，清单是图纸，载体是物流**。换合作商 = 换载体，引擎和图纸不动。
这条正好和 dago 的模式对齐（`package.yaml` 里 `baseImage` 按 sha256 钉死 = 基础镜像是**外部输入**，
派生镜像/载荷才是**我们的资产**）。

### 7.2 为什么种子能"免疫"基础镜像差异

种子**自己不装任何依赖**，因此不受基础镜像的 Python 环境、包管理器、init 系统影响。
它只依赖三件事，而这三件事在"最基础的镜像"上通常都成立：

1. 有一个 `python3`（合作商既然报 py3.10，就一定有）；
2. 能写 `/opt`（容器实例的 root）；
3. 能出网到某个镜像源，**或者**我们能通过 SSH/共享存储把 wheelhouse 送到。

对照我们自己的约定：bootstrap 本来就是"纯标准库 Python"（见项目约定），
**种子就是同一个约定的前置延伸**——先用它把环境装出来，再把接力棒交给 `start-bootstrap`。

### 7.3 实测：在基础镜像上到底还要装多少

基础镜像（九章 `alayanew-public/pytorch:2.8.0-...`）已经自带：

```
Ubuntu 22.04 · Python 3.11.11 (conda) · CUDA 12.8 (nvcc 12.8.93) · torch 2.8.0+cu128
```

需要额外装的：`sglang==0.5.19` + `mooncake-transfer-engine` + **118 个分布包**
（=`/opt/tai-talea/venv` 的 site-packages 相对 conda 基础环境 site-packages 的差集）。

体积构成（venv site-packages 共 8.8G）：

| 项 | 体积 | 说明 |
| --- | --- | --- |
| `nvidia/*` | 3.2G | 含 **cu13 变体**（`nvidia_nccl_cu13`、`nvidia_cudnn_cu13`…）→ **与基础镜像的 CUDA 12.8 重复** |
| `torch` | 1.2G | **重复**：基础镜像已有 torch 2.8.0，pip 又拉了一份 |
| `sgl_kernel` | 1.2G | 必需 |
| `triton` | 691M | 必需 |
| `nvidia_cutlass_dsl` | 451M | 必需 |
| `mooncake` | 282M | PD 分离必需 |
| `sglang` | 156M | 必需 |

→ **约 4.4G（50%）是与基础镜像重复的资产**。根因是 pip 没有约束到基础镜像已有的
torch / CUDA 版本。这是"在别人的基础镜像上装依赖"必须做的一步优化：
**用 `--constraint` 把 `torch`、`nvidia-*` 钉到基础镜像已有版本**，载荷可从 8.8G 压到 ~4G。
基础镜像的资产要**白拿**，不白拿就是白付带宽和磁盘。（待实测验证）

`wheelhouse` 实测 **3.9G / 206 个轮子**——这才是真正值得搬运的制品，且天然离线可用。

### 7.4 venv 不可搬运，锁文件可搬运

venv 里写死了绝对路径（`pyvenv.cfg`、脚本 shebang、部分 `.so` 的 rpath），
换目录或换机器就可能失效。所以正确做法**不是"造好 venv 搬过去"，而是"把锁文件搬过去、就地重建"**。

可搬运的制品只有两样：

- **锁文件**（几 KB）——必须；
- **wheelhouse**（可选）——仅用于离线场景；能出网时直接用镜像源更快。

### 7.5 载体的决策表

| 合作商给什么 | 载体 | 每台容器成本 |
| --- | --- | --- |
| NAS / 共享存储（可写、路径一致） | 挂载预置载荷，零拷贝 | **零安装**（最优） |
| 镜像能力（能指定自定义镜像） | 预构建派生镜像，开机即就绪 | **零** |
| SSH | scp 种子进去 → 容器自己拉 | 数十秒 + 安装时间 |
| 只有"启动脚本 / 云初始化"字段 | 种子内联（一行 `curl … \| python3 -`） | 同上 |
| 只有公网 | 种子 + 公网镜像源，清单里只留 requirements | 十余分钟/台 |
| 只有 API、无 shell | **必须由合作商预装**，或走对象存储下发 | 无解 |

对应本项目现状：九章**给 SSH**（已有），所以载体③立刻可用；
九章还有 NAS 型存储（§6 待确认），若可共享就是载体①。

### 7.6 凭据注入与载荷分离

同一份载荷对所有合作商复用，**凭据不进载荷**：

- `TAI_TALEA_BOOTSTRAP_TOKEN` 走**环境变量注入**（`start-bootstrap` 已是 env 优先、文件兜底）；
- 业务包凭据按实例下发（M3 签名业务包）。

这样"载荷"是可以公开复制的资产，"凭据"才是需要保护的对象——
与 §3 结尾那个"降的是镜像层暴露、不是运行期暴露"的边界判断一致。

### 7.7 清单（manifest）草案

```yaml
class: ubuntu2204-cu128-py311          # 兼容类，等价于 dago 的 compatibilityClass
base:
  os: ubuntu-22.04
  cuda: "12.8"
  python: "3.11"
apt: [pkg-config, libssl-dev, protobuf-compiler]
pip:
  requires: requirements.lock           # 钉死版本，含 sglang / mooncake
  constraints: base-image.txt           # 把 torch / nvidia-* 钉到基础镜像已有版本（§7.3）
  index: https://mirrors.bfsu.edu.cn/pypi/web/simple
wheelhouse:                             # 可选：离线时使用
  digest: sha256:...
  url: <制品库>/ubuntu2204-cu128-py311/wheelhouse.tar.zst
components:
  - {name: tai_talea_bootstrap, ref: <commit>, digest: sha256:...}
  - {name: sgl-model-gateway,  ref: <commit>, digest: sha256:...}
verify:
  - profile.json matches base
  - all component digests
```

### 7.8 三档规模

| 规模 | 做法 |
| --- | --- |
| 1~3 台（当前） | 种子 + 公网快源，手工触发；实测约 12 分钟/台 |
| 几十台 | 共享存储挂载 或 内网 wheelhouse；种子由控制面 `Prepare` 钩子自动推送 |
| 长期 | 镜像烤入（一次投入，开机即就绪）；载荷随版本推进，靠换镜像 tag |

**三档用的是同一份清单**，这正是把"装什么"和"怎么送"解耦的收益。
