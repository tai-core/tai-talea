## 2. 验收标准与证据

### 2.1 重复事件不会重复启动或回收实例

- `handleCapacityEvent` 先用 `event_id` 抢占（`INSERT ... ON CONFLICT DO NOTHING`）；抢占失败即
  返回 `{accepted:true, duplicate:true}`，**不进入任何 handler**。
- `TestAcceptanceDuplicateEventDoesNotRepeatLifecycle` 用假 bootstrap 的 `GET /bootstrap/status`
  调用次数做断言：重复投递前后探测次数不变、审计行数不变、实例仍为 IDLE。

### 2.2 非法状态转换会被拒绝并告警

- 三层防线：`domain.ValidateTransition`（图 + 组合）→ `controller.transition` →
  `store.ApplyTransition` 在事务内以**数据库当前行**为 `from` 重新校验（防止控制器 bug 或
  并发写入绕过规则）。
- 拒绝时：结构化 `ERROR` 日志 + `capacity_illegal_transitions_total{code}` +
  `illegal_state_transition` 告警，且**不落盘**。
- `TestAcceptanceIllegalTransitionIsRefusedAndAlerted` 断言了错误类型、`SeverityReject`、
  告警记录、磁盘状态未变、指标已累加。

### 2.3 新实例能从 ADDED 进入 IDLE

- `CAPACITY_ADDED` → 创建 `ALLOCATING` → `PREPARING`（同时写入 PREPARE operation）→
  `runPrepare` 执行 §7.1 六步 → `IDLE`。
- §7.1 六步的落点：endpoint 可达（`GET /bootstrap/health`）、租约有效（lease id + 观测时间
  在 `lease_warning` 窗口内）、GPU/CUDA/Python/SGLang/模型兼容矩阵（`GET /bootstrap/status`
  上报环境）、工作与日志目录（由 bootstrap 创建并在 status 中上报 wheelhouse/virtualenv，
  控制面只校验不执行命令）、bootstrap 版本一致。
- 失败时保留容器、累加 `prepare_attempts`、写 `PENDING` operation 等待重试；超过
  `prepare_max_attempts` 进入 `LOST` 并告警（`TestPrepareFailureKeepsTheContainerAndReports`、
  `TestEnvironmentMismatchIsDetectedBeforeStart`）。

### 2.4 服务能完成启动、健康检查和 Router 注册

- `IDLE + role` → `STARTING` →（`launcher.Start` + 轮询 health）→ `HEALTHY` → `REGISTERING`
  →（`POST /workers` + readiness 可路由）→ `SERVING`。
- SERVING 的六个前置条件全部落实：容器可达、SGLang health 通过、worker identity 已注册、
  role 正确、Router membership 存在、readiness 可路由。
- Router 已存在同 URL 的 membership 时通过 `GET /workers` 复用（`ErrAlreadyRegistered`），
  避免重复注册；`TestAcceptanceReconcileRecoversAfterRestart` 覆盖了这条路径。

### 2.5 摘流不会使用 DELETE

- `controller.RouterAdapter` 接口**没有**删除方法，从类型层面排除了"用 DELETE 摘流"。
- `TestAcceptanceRevocationDrainsThroughReadinessOnly` 的假 Router 统计 `DELETE /workers`
  调用次数，在注册、启动、摘流、停止、回收全流程后断言为 0，并断言 readiness 已变为
  `unavailable`、`DRAINING` 携带 deadline、bootstrap `stop` 恰好被调用一次、容器最终
  `RELEASED` 且已归还合作商。

### 2.6 控制面重启后能通过 reconcile 恢复状态

- 启动顺序：`Recover()`（放弃上次进程残留的 `PENDING` 事件 → 重放 operation → 逐实例对账）
  → 才对外提供 HTTP。
- 对账不会仅凭数据库把实例标记为 SERVING：`settleService` 重新注册 worker、核对 readiness
  generation，并只在验证通过后写回 SERVING。
- `TestAcceptanceReconcileRecoversAfterRestart` 先清空假 Router 的 worker 池（模拟 Router
  重启），再断言：worker 被重新注册且拿到新的 worker id、readiness 可路由、未发生 DELETE；
  第二轮恢复对账为零变更。

## 3. 与开发文档的差异

### 3.1 明确扩展（最小必要）

见 README §7。核心是 `capacity_instances` 的少量附加列、`audit_log` 表、运维接口，以及
Pull 机制的"已实现但默认关闭"。

### 3.2 刻意不做（属于 M2/M3）

- 多 Router、Redis 共享状态、Idle 缓冲与自动补位（M2）。
- PartnerAdapter 插件化（M2）——当前是编译期注册的 static / http 两种。
- 可自定义镜像、签名业务包、SHA256 + ed25519 校验、原子解压、灰度与回滚（M3）。
- 基于历史与线上负载的自适应 P/D 配比（M3）——`planner.LoadSnapshot` 只是预留输入面，
  `checkRatioDrift` 只做偏离告警，**不做**自动调整。

### 3.3 需要说明的实现取舍

1. **`DRAINING` 不新增容器状态**：文档 §7.3 的 `SERVING -> readiness=false -> DRAINING`
   发生在服务层，容器保持 `IDLE`。`IDLE + DRAINING` 是合法组合（见 `CheckCombination`）。
2. **角色转换分两轮**：`REASSIGN` 先摘流，下一轮再以新角色启动。这样避免在同一个端口上
   边摘流边重启服务，也让 `min_hold` 与 `cooldown` 有自然的作用窗口。
3. **`FAILED -> DRAINING` 这条边**是文档未列出但必需的：启动失败的 worker 仍可能留有
   membership，撤销容量时必须能把它停下来再归还容器，否则会卡在
   "still runs service state FAILED"。
4. **`/bootstrap/start` 接受 `extra_args` 白名单**：容器内进程不执行 shell，命令以参数
   向量构造，额外参数只允许文档化的 SGLang 开关，防止把 bootstrap 变成远程命令执行面
   （§9、§15）。
5. **版本匹配语义两侧一致**：控制面（`instancemanager.VersionMatches`）与容器 bootstrap
   （`profile._matches`）使用同一套规则——以 `.x` 结尾表示主版本线通配，否则要求完全一致。
   否则运维在 `image_profile.sglang` 写 `0.4.x` 时，控制面会接受 0.4.6 而容器自检拒绝，
   或反之，形成难以定位的"环境不匹配"。
6. **重投递与防重放的分工**：防重放由时间戳窗口 + 整体 HMAC 承担，幂等由 `event_id` 唯一
   约束承担；完全相同的重投递按 §5 返回幂等成功（200 + `duplicate:true`），并用
   `capacity_push_replays_total` 暴露重试行为，而不是返回错误让合作商无限重试。
7. **`/bootstrap/*` 的共享密钥（文档未规定，接入真实合作商后补上）**：
   文档 §9 只写了"容器内只运行一个受控的 bootstrap 进程"，没有规定接口鉴权，
   `server.py` 原本的注释甚至写着 *"The server binds inside the container only"*。
   接入九章智算云后确认**这个假设不成立**——该平台默认把容器端口（9001/9002）发布到
   公网并分配公网地址，而 bootstrap 原来的默认绑定是 `0.0.0.0` 且毫无鉴权。
   后果是任何人都能调 `/bootstrap/stop` 停服务，或用 `/bootstrap/start` 指定任意
   `model_path` 启动进程（`extra_args` 的白名单始终有效，但 `model_path` 当时无校验）。

   修法是两道独立屏障，两侧都 fail-closed：

   | | 容器侧 | 控制面侧 |
   | --- | --- | --- |
   | 绑定范围 | `--host` 默认改为 `127.0.0.1`；对外暴露必须显式写 `0.0.0.0` | — |
   | 鉴权 | 校验 `X-Bootstrap-Token`，密钥取自 `TAI_TALEA_BOOTSTRAP_TOKEN` 或 `--token-file`；**密钥为空则拒绝启动**（退出码 `71`） | `controller.bootstrap_token` 必填且 ≥16 字符，否则拒绝加载配置；`launcher.New` 拒绝空密钥 |

   鉴权先于路由：未带密钥访问未知路径返回 `401` 而不是 `404`，不泄露路径是否存在。
   密钥比较用 `hmac.compare_digest`，"密钥错误"与"没有密钥"返回完全相同的响应体。

   一个密钥覆盖整个部署，而不是按合作商/实例分发——合作商平台只允许在控制台创建实例，
   密钥必须由人在两侧手工对齐；按实例分发需要程序化创建实例，而平台未开放该接口。
   代价（单密钥泄露影响全部容器）与原因一并记录在 README §7。

## 4. 本地验收演练

```bash
make test                                  # Go 全量 + bootstrap 单测
make check-config CONFIG=deploy/tai-talea.example.yaml
go test ./internal/controller/... -run Acceptance -v
```

`Acceptance*` 系列测试是一个进程内的端到端演练：真实 SQLite、真实 HTTP 客户端、
假 Router（覆盖 `POST /workers`、`GET /workers`、`GET|PUT /state/workers/{id}`、
`GET /get_loads`、`DELETE /workers/{id}`）与假容器（覆盖
`/bootstrap/health|status|start|stop`）。
