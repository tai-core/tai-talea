# Talea 使用说明书

适用于已经配置好 Talea、Router 和安装制品的控制节点。首次搭建控制节点见 [项目说明书](project-guide.md)。

## 1. 访问管理页面

Talea 默认在控制节点监听 `127.0.0.1:8787`。在**自己的电脑**运行并保持 SSH 连接：

```bash
ssh -N -L 18887:127.0.0.1:8787 -p <控制节点SSH端口> <账号>@<控制节点地址>
```

本机浏览器打开 `http://127.0.0.1:18887/`。这条 SSH 转发把本机网页请求送到控制节点。

管理员在控制节点运行 `talea login-token` 获取页面令牌。合作商使用单独分配的页面令牌，只能操作自己名下的节点。令牌不写入浏览器持久存储，刷新页面后需要重新登录。

## 2. 上线节点

1. 点击右上角“上线”。
2. 填写节点名、合作商、SSH 地址、端口、账号、密码或无口令私钥。当前安装需要 root 权限。
3. 内网服务地址默认自动探测；高级设置可指定控制节点和 P/D 节点均可达的地址，以及 SSH 主机指纹。
4. 提交后查看“上线任务”的阶段；最终以节点列表显示“服务中”为准。安装完成但容量已达到上限时，节点可能保持“空闲”。

Talea 自动完成环境检查、运行时与模型分发、安装、自检、bootstrap 启动和纳管，再由 Planner 分配 P 或 D。关闭页面不影响后台执行。失败任务显示原因；修正后使用“修改并重试”，重新填写凭据。安装成功或终态失败后，任务记录中的 SSH 凭据会被清除。

已回收节点可以“重新上线”，产生新租约。同名旧任务保留历史并显示“已下线”。正在运行的节点不允许直接覆盖安装。

节点必须具备受支持的 NVIDIA 驱动/GPU、Python、系统软件源，以及控制节点与工作节点、P 与 D 之间的数据网络。只有公网 SSH 映射不代表 P/D 数据网络可用。当前版本只接管管理员预先验证的系统/CUDA/Python/模型组合。

## 3. 回收节点

点击对应节点的“回收”，确认最长等待时间后提交。也可以在控制节点运行：

```bash
talea reclaim <节点名> --grace 60
```

流程是：保存回收意图 → 关闭 Router readiness → 等待在途请求 → 停止 SGLang → 释放容量。未知负载会继续等待；超过宽限期允许强停。停止失败时保留回收意图并重试，禁止重新分配服务。

“请求已接受”不等于回收完成；以“已回收”（`RELEASED + NONE`）为准。回收最后一个 P 或 D 会影响推理可用性。

**static 模式只停止推理服务并从 Talea 回收，平台容器仍保留。** 配置真实 HTTP 释放接口后，才会调用合作商平台释放容器。

## 4. 查看状态和负载

```bash
talea nodes                 # 合成后的节点状态
talea nodes --raw           # 附带底层状态字段
talea status <节点名>        # 详细状态
```

页面每 3 秒刷新，节点“详情”显示最近错误和审计记录。

| 指标 | 含义 |
|---|---|
| GPU 资源 | SSH 上线时通过 nvidia-smi 探测；Push 节点则来自合作商上报。不是服务实际用卡数 |
| P / D | Planner 分配；监控再核对 SGLang 实际运行角色与 Router 注册角色 |
| P 输入 / D 输出 token/s | 相邻采样的已完成请求 token 计数差，不能直接比较两者大小判断配比好坏 |
| 运行 / 等待 | 正在执行的请求及调度、预分配队列 |
| KV 在途 / 缓存占用 | KV 传输中的任务及缓存使用情况 |
| 并发压力 | `(运行 + 等待) / 实际并发上限`，可超过 100%，不是 GPU 利用率 |
| “—” / 未知 | 指标缺失、首次采样或过期，不代表零负载 |

图表保留约五分钟采样，可悬停或用左右方向键查看。Talea 重启后曲线重新积累。SGLang 的空闲指标可能延迟约 30 秒更新。当前 Planner 仍按固定档位工作，看板负载不会自动改变 P:D 配比。

## 5. 在控制节点发测试请求

客户端配置需有 `router_url` 和 `model`，然后运行：

```bash
talea benchmark --requests 64 --concurrency 8 --max-tokens 256
# 持续约一分钟的观察示例，实际时长取决于机器：
talea benchmark --requests 512 --concurrency 8 --max-tokens 256
```

首次下载固定版本 GSM8K，之后复用校验过的缓存。流量由**运行该命令的机器**发出，因此请在控制节点执行。默认排除 2 个预热请求，报告包括成功/失败请求数、请求/Token 吞吐、首 Token 延迟（TTFT）和平均逐 Token 延迟（TPOT），保存在 `/opt/tai-talea/benchmarks/`。

`Ctrl+C` 停止提交后续请求；已发出的请求等待返回或超时。运行锁残留时，先确认锁文件中的进程已退出再清理。压测用于观察当前配置表现，不代表准确率或生产最大承载能力。

## 6. 合作商用简短指令推送容量

管理员分配独立的 `partner.json`（服务地址、`partner_id`、`push_token`、`push_secret`），权限设为 0600：

```bash
talea --config partner.json push add --file node.json
talea --config partner.json push revoke <节点名> --grace 60
```

`node.json` 示例：

```json
{
  "id": "worker-1",
  "endpoint": "http://10.0.0.12:9001",
  "service_endpoint": "http://10.0.0.12:9002",
  "lease_id": "lease-unique-1",
  "spec": {"gpu": "H100", "gpu_count": 4}
}
```

Push ADD 登记的是**已有且 bootstrap 已准备好的容量**；需要首次 SSH 安装时使用页面“上线”。客户端自动签名。同一事件重试使用输出中的 `--event-id 原ID`，保持容量字段不变；新一轮供给使用新事件 ID 和新租约。

## 7. 常见问题

| 现象 | 处理 |
|---|---|
| 本机打不开页面 | 检查 SSH 转发仍在运行、本机 18887 是否冲突、控制节点 /readyz 是否可达 |
| 上线失败 | 看任务错误及工作节点 /opt/tai-talea/logs/onboarding.log，核对 SSH、磁盘、兼容版本和网络 |
| 显示节点失联 | 检查 bootstrap 9001、容器网络；恢复后由 Talea 重新探测 |
| 一直回收中 | 查看最近错误；确认 Router、停止接口和平台释放接口正常，勿手工把数据库改成 RELEASED |
| 两侧均服务中但推理失败 | 查看实际角色、Router 健康/readiness、P/D 数据端口和 SGLang 日志；Router 异常池状态可能仍需维护恢复 |
| 服务启动失败且重试耗尽 | 修正具体故障后，用受控回收→重新上线重试；不要对仍运行的服务直接重装 |

当前测试环境的地址和访问方式另见 [管理页面与客户端](console-and-client.md)，生产部署使用各自配置。
