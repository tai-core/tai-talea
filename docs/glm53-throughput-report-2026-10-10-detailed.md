# GLM-5.3-Flash 推理吞吐性能报告（九章智算云）

> **口径与结构参考**：《商汤集群压测报告》（结论先行 → 集群与测试配置 → 实测结果 → 稳定性与缓存 → 复现）。
> **数据来源**：2026-10-10 在**九章智算云（Alaya NeW Cloud）CCI 实例**上的真机实测，全部数字可在 §8 的原始日志里逐条核对，无估算值。
> **平台边界**：本报告**只使用九章平台的机器**。此前在其它平台（中国移动 AI 平台 nightshift 租户）跑过的 PD 数据一律未采用，两种平台的数据不混称、不对比。

## 结论

**本轮在九章智算云两台 CCI 实例（各 8×H100 80GB）上，用同一套客户端、同一种负载，把 GLM-5.3-Flash 的两种部署形态各测了一遍。**

| | 形态一：双节点聚合副本 | 形态二：PD 分离 1P1D |
| --- | --- | --- |
| 短输入 / 512 输出，峰值输出吞吐 | **3,133 tok/s**（conc=32） | **2,889 tok/s**（conc=64） |
| 折算每节点输出吞吐 | **1,567 tok/s / 节点** | **2,889 tok/s / decode 节点** |
| 长输入 16K 冷预填充，输入吞吐 | **32,903 tok/s**（conc=8） | **14,706 tok/s**（conc=8） |
| 长输入 16K 端到端总吞吐峰值 | **33,382 tok/s ≈ 200 万 TPM** | **14,923 tok/s ≈ 89.5 万 TPM** |
| 单流吞吐 | **186 tok/s**（开 EAGLE） | **97.6 tok/s**（PD 下投机不可用） |
| 前缀缓存 | **生效**，16K 输入下命中 73.2%，TTFT 0.94 s → 0.20 s | **默认不生效**（`cached_tokens` 恒为 0） |

**三个可以直接用于容量规划的结论：**

1. **聚合副本的容量拐点在 conc=32，不在「越大越好」。** 输出吞吐从 conc=1 的 186 tok/s 线性涨到 conc=32 的 3,133 tok/s（16.8×），但 **conc=64 反而回落到 1,494 tok/s**，同时 TTFT P50 从 1.12 s 恶化到 7.66 s、每请求吞吐从 103 掉到 44 tok/s。这是 KV 池被压满后出现抢占重算的典型形状，**不是「再加并发还能涨」**。

2. **PD 把 decode 节点的产出效率提高了约 1.8 倍，代价是单流腰斩。** PD 的 decode 节点不做预填充，全部 8 张卡只服务解码，conc=64 时单节点就产出 2,889 tok/s，高于聚合形态每节点 1,567 tok/s；但因为 PD 下投机解码（EAGLE）不可用，单流吞吐从 186 掉到 97.6 tok/s（-47%）。

3. **长输入场景两者差距是结构性的：聚合有 2 个节点都能吃预填充，PD 只有 1 个。** 16K 冷输入下聚合 conc=8 达到 32,903 tok/s 输入吞吐，PD 同档 14,706 tok/s，比值 **2.24×**，正好等于预填充节点数之比（2 ∶ 1）。PD 要缩小这个差距只能加 prefill 节点，或缩短输入。

### P / D 单节点吞吐预估

| 角色 | 单节点吞吐（实测折算） | 折算承载能力 | 备注 |
| --- | --- | --- | --- |
| **P（prefill）** | **14,706 tok/s 输入**（16K 档，conc=8） | 0.85 req/s @17.35K 输入 | 短输入档远高于此，本报告未单独测其上限 |
| **D（decode）** | **2,889 tok/s 输出**（短输入，conc=64） | 5.6 req/s @512 输出 | 长上下文 KV 变大，实际低于此值 |

**瓶颈落在哪一侧，取决于输入输出比**：

- 短输入（39 in / 512 out）→ **D 是瓶颈**，P 侧几乎闲置 ⇒ 1P1D 整体 ≈ **2,889 tok/s**（与实测吻合）；
- 长输入（17.35K in / 256 out）→ **P 是瓶颈**，D 利用率 < 8% ⇒ 1P1D 整体 ≈ **0.85 req/s ≈ 217 tok/s 输出**（与实测吻合）。

**P∶D 配比估算式**：`N_P : N_D ≈ (I / P_tput) : (O / D_tput) ≈ 0.196 × (I / O)`

| 负载 | 输入∶输出 | 预估 P∶D |
| --- | --- | --- |
| 短输入长输出（W1） | 39 : 512 | **1 : 67** —— P 可大量省略 |
| 长输入短输出（W2） | 17,350 : 256 | **13 : 1** —— P 是绝对主力 |

> 配比完全由「输入输出比 ÷ 两角色吞吐比」决定，不是固定值。D 的吞吐取短输入档（其最好情况），长上下文下会下降 ⇒ W2 的 13∶1 是偏高估计。

**另有一个必须写进运维手册的实测现象**：`--mem-fraction-static` 与投机解码的组合、以及**服务自己报告的前缀缓存命中率**，是本轮唯一两处「不测就会误判」的地方，详见 §2.4 与 §5.2。

### 1.4 负载口径

两种形态跑**完全相同的两组负载**，同一个客户端（`bench2.py`，流式 SSE + `stream_options.include_usage`，token 数取自服务端 `usage`，不靠估算）：

| | W1「交互式生成」 | W2「长上下文」 |
| --- | --- | --- |
| 输入长度 | 39 token | **≈17,350 token**（实测均值） |
| 输出长度 | 512 token | 256 token |
| 并发 | 1 / 2 / 4 / 8 / 16 / 32 / 64 | 1 / 2 / 4 / 8 |

## 2. 形态一：双节点聚合副本

### 2.1 单副本基线（直连 `:9002`）

| 场景 | 输出吞吐 | TTFT P50 / P90 | TPOT 均值 | 端到端 P50 |
| --- | --- | --- | --- | --- |
| 单流（conc=1） | **186.0 tok/s** | 0.154 s / 0.155 s | 5.09 ms | 2.756 s |
| conc=4 | **560.8 tok/s** | 0.171 s / 0.373 s | 6.65 ms | 3.573 s |

单流 186 tok/s、TTFT 0.15 s、TPOT 5.09 ms，多次测量极稳（冷热两遍差 < 0.1%）。作为对照，本项目 2026-09-23 在同型号 H100 节点上测得的**无投机解码**单流基线为 **113.4 tok/s** —— **开 EAGLE 后 +64%**，这是聚合形态相对 PD 形态最大的单项优势来源（PD 下投机不可用）。

| 64 | 1,493.9 | 1,607.7 | **7.659 s** | **16.952 s** | 9.42 ms | 16.103 s | 43.6 | — |

```
聚合输出吞吐 (tok/s)
 3,133 |                                          ██
 1,793 |                                 ██       ██
 1,139 |                        ██       ██       ██
   615 |            ██          ██       ██       ██
   371 |     ██     ██          ██       ██       ██
   186 | ██  ██     ██          ██       ██       ██

        c1  c2      c4         c8        c16      c32  c64
```

**要点**：

- **conc=2 恰好 2.00×**：Router 轮询分流零损耗，两个副本各承担一半。
- **conc=32 是峰值**，3,133 tok/s，折合 **1,567 tok/s / 8×H100 节点**。此时每请求吞吐仍有 102.7 tok/s（单流的 55%），TTFT 1.12 s —— 属于「算力被摊薄但尚未崩」的状态。
- **conc=64 是明确的容量墙**。输出吞吐掉到 1,494 tok/s（比 conc=32 低 52%），TTFT P90 飙到 **16.95 s**，每请求吞吐只剩 43.6 tok/s。原因不是排队而是 **KV 池被压满后 decode 序列被抢占重算**：此时每副本在跑 32 个并发序列（= `--max-running-requests 32`），`--mem-fraction-static 0.60` 留给 KV 的显存不足以同时容纳 32 × 512-token 上下文。
- 两个副本的分流是均匀的：**conc=2 时聚合吞吐恰好是单流单副本的 2.00×**（371.3 vs 186.0），说明 Router 轮询零损耗。

### 2.3 W2：长输入（≈17.4K token）/ 256 输出

**（a）冷预填充 —— 每个请求都真的从头算完 17.4K token**（每次运行用独立 nonce，杜绝上一轮的 radix cache 残留）：

| 并发 | 输入吞吐 | 输出吞吐 | 端到端总吞吐 | TTFT P50 | 缓存命中 |
| --- | --- | --- | --- | --- | --- |
| 1 | **8,908** | 130.8 | 9,038 | 0.756 s | 0% |
| 2 | **17,404** | 252.7 | 17,657 | 0.751 s | 0% |
| 4 | **23,948** | 346.1 | 24,294 | 0.769 s | 0% |
| 8 | **32,903** | 479.3 | **33,382** | 1.713 s | 0% |

冷预填充下 conc=1 单流只有 8,908 tok/s，扩到 conc=8 达 32,903 tok/s（**3.7×**），TTFT 仍只有 1.7 s —— 预填充不是这两台机器的瓶颈。折合 **16.5K tok/s / 节点**的原始预填充能力。

**（b）90% 共享前缀 —— 多轮 / Agent 形状**（顺序 16 个请求，前缀相同、尾部不同）：

| 指标 | 值（3 次复跑中位数） |
| --- | --- |
| 输入吞吐（含缓存命中） | **11,523 tok/s** |
| 其中真正需要预填充的 | **3,090 tok/s** |
| **缓存命中率** | **73.18%**（3 次完全一致） |
| TTFT P50 | **0.202 s** |
| 端到端总吞吐 | 11,751 tok/s |

**同一条 17.4K 输入，命中前缀缓存后 TTFT 从 0.756 s 降到 0.202 s（-73%），输入吞吐从 8,908 涨到 11,523 tok/s。** 命中率 73.18% 而非 90%，是因为 16 个请求里第 1 个必然全冷，且 chat template 等固定前缀也计入分母。

这正是《商汤集群压测报告》所描述的业务形状（长输入 + 高前缀复用）：**吞吐数字必须与命中率一起读**，否则同一个系统可以因为缓存冷热差出 3 倍以上。

### 2.4 冷启动 vs 稳态：服务期 kernel 编译的代价

同一个并发点连跑两遍，第一遍与第二遍的差距（取自 `agg-sweep.log`；§2.2 中 conc≥16 用的是同一批运行的 3 次复跑中位数，与下表的 hot 遍相差 < 1%）：

| 并发 | 第一遍（cold） | 第二遍（hot） | 差距 |
| --- | --- | --- | --- |
| 8 | 1,110.2 | 1,138.5 | +2.5% |
| 16 | 1,765.3 | 1,811.9 | +2.6% |
| 32 | 3,073.9 | 3,145.6 | +2.3% |
| **64** | 2,773.0 | 1,501.5 | **−46%** |

conc ≤ 32 时冷热差异只有 2–3%（这些 batch size 在之前的预热里已经编译过）。**conc=64 上「cold 比 hot 快」是假象**：两次都处在 KV 抢占的工况里，差异来自抢占的随机性而非编译。真正需要标注的是**首次遇到某个 batch size 时引擎会停摆数秒**——SGLang 自己就会告警：

> `Triton kernel '...' took 3.05 s to compile after serving started. Serving-time compilation can stall the engine; pre-compile it during engine init.`

**上线前必须按目标并发档位预热一遍**，否则会把「冷编译」误读成「容量上限」。

## 3. 形态二：PD 分离 1P1D

### 3.1 部署与 KV 传输（九章上的可行性）

PD 的前提是**两台 CCI 实例之间能传 KV**。这是 KVM + VXLAN 的云容器实例，所以先验证再部署：

| 检查项 | 结果 |
| --- | --- |
| RDMA 设备 | 两节点各有 `ib7s400p0…p7`（8 × 400G，MT4129/ConnectX-7）+ `ib6s200p0` + `mlx5_bond_0`，全部 `PORT_ACTIVE` |
| IB 子网 | 两节点 `subnet_prefix` 相同、`sm_lid = 1` —— **同一 IB 子网** |
| **实测带宽** | `ib_write_bw -d ib7s400p0` 两节点互测：**386.48 Gb/s**（400G 端口近线速） |
| 传输后端 | SGLang 内置 mooncake transfer engine **0.3.13**（已随 venv 安装） |
| 端到端确认 | decode 侧日志 `rdma_endpoint.cpp: Received RDMA ready ACK.` —— KV 确实经 RDMA 送达 |
| 部署结果 | Router 识别 **1 个 `worker_type=prefill` + 1 个 `worker_type=decode`**，均 `is_healthy: true` |

**结论：九章 CCI 实例之间具备做 PD 分离的完整物理条件，且是 RDMA 而非 TCP。** 这一条值得单独记录——PD 能不能落地往往就取决于这一项，而它取决于云厂商是否把 IB 直通给了容器实例。

### 3.2 W1：短输入 / 512 输出

| 并发 | 输出吞吐 | 端到端总吞吐 | TTFT P50 | TTFT P90 | TPOT | 端到端 P50 | 每请求 tok/s | 线性度 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 97.6 | 105.0 | 0.174 s | 0.185 s | 9.92 ms | 5.241 s | 97.6 | 100% |
| 2 | 178.0 | 191.5 | 0.317 s | 0.457 s | 10.59 ms | 5.729 s | 89.0 | 91% |
| 4 | 329.4 | 354.5 | 0.315 s | 0.400 s | 11.51 ms | 6.201 s | 82.4 | 84% |
| 8 | 601.8 | 647.6 | 0.463 s | 0.480 s | 12.54 ms | 6.840 s | 75.3 | 77% |
| 16 | 1,055.1 | 1,135.4 | 0.739 s | 0.756 s | 14.12 ms | 8.026 s | 66.1 | 68% |
| 32 | 1,904.2 | 2,049.3 | 1.130 s | 1.173 s | 15.25 ms | 8.887 s | 59.7 | 61% |
| 64 | **2,888.7** | 3,108.7 | 2.150 s | 2.180 s | 17.85 ms | 11.278 s | 45.4 | 46% |

（单位 tok/s。cold/hot 两遍差异 < 1%，除 conc=32 的 cold 一遍撞上编译，已在表中剔除。）

**要点**：

- **一直涨到 conc=64 才到 2,889 tok/s，没有出现聚合形态 conc=64 那样的回退。** 因为 decode 节点独占 8 卡、`--max-running-requests 128`，KV 池（`mem-fraction 0.85`）空间充裕。
- **单节点产出效率更高**：PD 只有 1 个 decode 节点，conc=64 时它产出 2,889 tok/s，而聚合形态每节点只有 1,567 tok/s。**PD 把「解码」这件事做得更专。**
- **代价是单流**：97.6 tok/s vs 聚合 186 tok/s（**-47%**），且 TPOT 从 5.08 ms 劣化到 9.92 ms。前者是因为 PD 下 EAGLE 不可用（+64% 的红利没了），后者是因为每个请求都要多走一次跨机 KV 交接。

### 3.3 W2：长输入（≈17.4K token）

| 并发 | 输入吞吐 | 输出吞吐 | 端到端总吞吐 | TTFT P50 | 缓存命中 |
| --- | --- | --- | --- | --- | --- |
| 1 | 4,999 | 72.8 | 5,145 | 0.940 s | 0% |
| 4 | 13,022 | 186.8 | 13,209 | 2.04 s | 0% |
| 8 | **14,706** | 217.0 | 14,923 | 5.00 s | 0% |

（95% 共享前缀的 16 请求顺序跑，PD 侧 `cached_tokens` 恒为 0、`cache_hit_pct = 0`，但 TTFT 从 0.940 s 降到 0.231 s，说明复用收益部分存在，只是**当前配置下无法量化**。）

**两个与聚合形态结构性不同的地方**：

1. **预填充能力只有一半**。16K 冷输入 conc=8，聚合 32,903 tok/s vs PD 14,706 tok/s，比值 **2.24×**，与预填充节点数之比（2 ∶ 1）一致。PD 把预填充集中到 1 个节点，长输入场景就必然吃亏。
2. **TTFT 随并发快速恶化**（0.94 s → 5.00 s）。所有请求的预填充都排在同一个节点前，此时它既是瓶颈也是单点。
3. **前缀缓存在 PD 模式下默认不生效**（需要显式开 `--disaggregation-decode-enable-radix-cache`）。对高前缀复用业务，这是 PD 形态最大的未开发项。

## 4. 两形态横向对照

同为九章两台 8×H100，同负载、同客户端：

| 维度 | 形态一：聚合副本 | 形态二：PD 1P1D |
| --- | --- | --- |
| W1 输出吞吐峰值 | **3,133 tok/s**（conc=32） | **2,889 tok/s**（conc=64） |
| W1 端到端总吞吐峰值 | 3,372 tok/s | 3,109 tok/s |
| W1 每节点输出吞吐 | 1,567 tok/s | **2,889 tok/s（decode 节点）** |
| W1 单流吞吐 | **186.0 tok/s** | 97.6 tok/s |
| W1 单流 TPOT | **5.08 ms** | 9.92 ms |
| W1 高并发是否回退 | **是**，conc=64 掉 52% | 否，conc=64 仍在上行 |
| W2 冷输入吞吐（conc=8） | **32,903 tok/s** | 14,706 tok/s |
| W2 端到端总吞吐峰值 | **33,382 tok/s ≈ 200 万 TPM** | 14,923 tok/s ≈ 89.5 万 TPM |
| 前缀缓存 | **生效**（16K 输入命中 73.2%） | 默认不生效 |
| 投机解码 EAGLE | **可用**（+64%） | **不可用** |
| `--mem-fraction-static` | 0.60（受投机约束） | 0.85 |
| 扩展方式 | 加副本（Router 轮询，conc=2 零损耗） | 调 P∶D 配比 + 加节点 |
| 资源解耦 | 无（prefill/decode 争同一批 GPU） | **有** |
| 单点风险 | 无（两副本互为备份） | **prefill 节点是单点** |
| 适合负载 | 交互式生成、短输入长输出、需要低 TTFT | 长输入短输出、需要 prefill/decode 独立扩容 |

**不可比因素（必须说明）**：两者单流差距 47% 里，**主要来自 EAGLE 的开关**而非 PD 架构本身——PD 与投机解码在 SGLang 0.5.20 下互斥。因此上表不构成「聚合优于 PD」或反之的结论。

**可以成立的判断**：

1. 如果负载是**交互式生成**（短输入、长输出、在意 TTFT/TTFT 与单流速度）→ **聚合副本**：单流快 90%，还能靠加副本线性扩。
2. 如果负载是**长输入、且并发很高**（比如代码仓库级上下文、批量文档处理）→ 两者都行，但 **PD 必须在 prefill 侧加节点**，否则 1 个 prefill 节点会把 TTFT 拖到秒级；1P1D 只在「长输入但低并发」时划算。
3. 如果业务有**高前缀复用**（多轮对话、Agent 反复读同一份长文档）→ **当前只有聚合形态吃得到这份收益**（73% 命中、TTFT 降 73%）。PD 要拿到同等收益必须先开 decode 侧 radix cache 并重测。

## 5. 稳定性、边界与口径说明

### 5.1 与《商汤集群压测报告》的口径对照

| 维度 | 商汤报告 | 本报告（九章） |
| --- | --- | --- |
| 硬件 | 5 台 × 8×B300，共 40 GPU | **2 台 × 8×H100，共 16 GPU** |
| 推理角色 | 3P + 2D | 2 副本聚合 / 1P1D |
| 负载 | 平均输入 ≈9 万 token，输入输出比 ≈100∶1 | 39 token 或 **≈1.74 万 token**，输出为主或 68∶1 |
| 缓存 | hicache 本地 POSIX L3，命中 90–92% | SGLang radix 前缀缓存，实测 **73.18%**（16K 输入档） |
| 吞吐口径 | Gateway 结算流量，总吞吐 **6,056–6,398 万 TPM** | 压测客户端实测，总吞吐 **89.5 万 – 200 万 TPM** |
| TTFT | P50 2.25 s / P90 3.93 s（峰值窗口） | 冷输入 conc=8 时 1.71 s；缓存命中时 0.202 s |

**为什么差约 32 倍**：商汤的 TPM 由「命中缓存的输入 token」主导（92% 命中 × 9 万长输入），单台 prefill 的输入处理能力就有约 2,000 万 TPM；本报告最高档是 16×H100、1.74 万输入、缓存全冷。**两者是不同维度的能力，不是同一把尺子的高低。** 若按 GPU 数归一化，商汤约 160 万 TPM/GPU，本报告约 12.5 万 TPM/GPU，差距主要来自 **B300 vs H100 的代际差、以及命中缓存的输入 token 不计入实际计算量**。

### 5.2 已知边界与运维注意项

| 项 | 说明 | 影响 |
| --- | --- | --- |
| **容量拐点在 conc=32** | 聚合形态 conc=64 输出吞吐反而掉 52%，TTFT P90 达 17 s | 不要用「最大并发」做容量规划；按 32 配，并用 LRU 限流 |
| **服务期 kernel 编译** | 首次遇到新 batch size，引擎停摆数秒（SGLang 自身会告警） | 首轮数字不能当容量上限；上线前按目标并发预热 |
| **PD 与投机解码互斥** | SGLang 0.5.20 下 PD 模式下 EAGLE 不启动 | PD 形态拿不到 +64% 的单流收益 |
| **PD 默认无前缀缓存** | `cached_tokens` 恒为 0，需 `--disaggregation-decode-enable-radix-cache` | 高前缀复用业务在 PD 下会白吃一份预填充 |
| **`mem-fraction-static` 强耦合投机** | 开投机时 0.70 必 OOM，须降到 0.60 | 报错形如 `illegal memory access`，不是 OOM |
| **PD 的 prefill 是单点** | 1P1D 下所有预填充排在一个节点 | TTFT 随并发线性劣化（0.94 s → 5.00 s） |
| **缓存命中率必须与吞吐同时读** | 同一系统冷/热前缀差 3 倍以上 | 单看 TPM 会把缓存热度误当成性能提升 |

## 6. 结论与建议

1. **可写进容量规划的数字**（九章智算云，2 × 8×H100，GLM-5.3-Flash FP8）：
   - 聚合副本：**1,567 tok/s 输出 / 节点**（短输入长输出、开 EAGLE、conc=32）；
   - 聚合副本长输入：**16.5K tok/s 原始预填充 / 节点**；
   - PD 1P1D：**2,889 tok/s 输出 / decode 节点**（conc=64），但单流只有 97.6 tok/s。
2. **交互式生成类负载上聚合副本**；**长输入且高并发上 PD 并加 prefill 节点**；**高前缀复用业务留聚合**（或先给 PD 开 decode 侧 radix cache 再评估）。
3. **上线前必做三件事**：按目标并发档位预热（消除冷编译）、确认 RDMA 设备清单（PD 形态）、按 `max-running-requests` 与 KV 池大小核算并发上限（避开 conc=32 之后的回退区）。
4. **建议补测（按优先级）**：
   - 给 PD 开 `--disaggregation-decode-enable-radix-cache`，重测长输入高复用档，与聚合的 73.18% 命中做同尺子对比；
   - 把聚合的 `--mem-fraction-static` 提到 0.70+（关掉 EAGLE）重测，隔离「投机 +64%」与「KV 池翻倍」两个变量对 conc=64 回退的贡献；
   - 3P1D 或 2P1D 多 prefill 节点的 PD 配比测试，验证 2.24× 是否随 prefill 节点数线性改善；
   - 把输入推到 32K（`--context-length` 上限）重测，向商汤的 9 万 token 口径再靠一步。

**测量方法学要点**（本轮踩过、后续必须遵守）：

1. **长输入必须带 per-invocation nonce**。prompt 若逐轮相同，第二轮的 `cached_tokens` 会告诉你「命中 99.86%」——那不是系统变快了，是上一轮把缓存留下来了。
2. **前缀复用要顺序发**。并发同时到达的请求互相不能复用前缀，只有多轮 / 串行形状才吃得到缓存。
3. **`cached_tokens` 在 `usage.prompt_tokens_details` 里**，不在 `meta_info`，且必须开 `--enable-cache-report`；不开就是恒 0，会把「没启用」误读成「没命中」。
4. **冷热各跑一遍**，否则会把服务期 kernel 编译的停摆（数秒）当成容量上限。
5. 灌 `--host` 时注意平台差异：九章 CCI 的两台实例是独立主机，端口不冲突；k8s `hostNetwork` 环境下则相反。
