# GLM-5.3-Flash on 4×8 H100 部署方案书

版本：v1.0　日期：2026-10-08　状态：待评审
适用范围：4 台 8×H100 80GB 容器实例（共 32 卡）承载 GLM-5.3-Flash 在线推理

---

## 0. 一句话结论

**采用「4 台各跑一个完整 TP8 聚合副本 + 聚合 Router 前置分流」的横向扩展形态。**
每台机器是一份自洽的、可独立启停的 GLM-5.3-Flash 完整服务（MTP 投机解码与 CUDA graph 全开），Router 只做负载均衡、不做 PD 解耦。

预测能力：单流 **186 tok/s**（与 2 节点持平），热态聚合吞吐 conc=32 约 **4,000–4,600 tok/s**，conc=16 约 **2,500 tok/s**。

该形态是当前唯一能同时拿到「多台 8 卡 + MTP + CUDA graph」的布局——官方 cookbook §3.5 明确：PD 分离下投机解码不启动，二者当前不可兼得。

## 2. 实测依据（不是推算，是已验证数据）

本方案的所有参数来自 2026-10-08 在两台 8×H100 上的实测（报告见 `glm53-layout-c-benchmark-2026-10-08.md`）：

| 指标 | 实测值 |
| --- | --- |
| MTP + CUDA graph 同开 | ✅ 跑通（`--mem-fraction-static 0.60`） |
| 单流吞吐 | 186 tok/s（无投机基线 113.4 tok/s，**+64%**） |
| TTFT | 0.15–0.19 s |
| EAGLE 接受长度 | 2.65–3.65（社区报告 2.99） |
| 每卡显存 | 51.6 GB（权重 37.98 + KV + CUDA graph） |
| 权重加载 | ramdisk 流式 **7.4 GiB/s**（305.8 GiB / 41 s） |
| 2 副本聚合吞吐 | conc8 **~1,170**；conc16 **2,026** tok/s |

**2 节点已验证的聚合曲线（视为 4 节点的标定基础）**

| 总并发 | 每副本 bs | 实测聚合吞吐 |
| --- | --- | --- |
| 1 | 1 | 186 |
| 2 | 1 | 372（恰好 2.0×） |
| 4 | 2 | 622 |
| 8 | 4 | 1,153–1,183 |
| 16 | 8 | 2,026 |

## 3. 为什么选横向 4 副本（方案比选）

| 方案 | 形态 | MTP | CUDA graph | 结论 |
| --- | --- | --- | --- | --- |
| **A（推荐）** | 4 × 独立 TP8 聚合副本 + Router | ✅ | ✅ | **采纳**。线性扩展、无跨节点依赖 |
| B | 2P2D PD 分离 | ❌ | 仅 decode 侧 | 长上下文/超大批量吞吐更优，但放弃 MTP 的 +64%，运维复杂度高 |
| C | 3 副本 + 1 备用 | ✅ | ✅ | 作为 A 的**上线过渡形态**（见 §7.1） |
| D | TP16 跨 2 节点 ×2 组 | ✅ | ✅ | **否决**。容器网络无 RDMA，TP16 跨节点 all-reduce 会成为瓶颈；且单点故障域放大 |

否决 D 的关键理由：本容器环境的跨节点链路仅为 overlay 内网（172.19.x.x），实测 PD 场景下只能用 `mooncake_tcp`。TP16 每层都要跨节点 all-reduce，时延不可接受。

## 4. 目标架构

```
                        ┌───────────────────────────────────────────┐
   客户端 ─────────────▶│  sgl-model-gateway  :30000                │
                        │  mode: Regular（非 PD）                    │
                        │  policy: cache_aware                      │
                        │  控制面 :30001                            │
                        └───┬────────┬────────┬────────┬───────────┘
                            │        │        │        │
              ┌─────────────▼──┐ ┌───▼────────┐ ┌─────▼──────┐ ┌────────────▼───┐
              │ node-1         │ │ node-2     │ │ node-3     │ │ node-4         │
              │ 8×H100         │ │ 8×H100     │ │ 8×H100     │ │ 8×H100         │
              │ TP8 / EP8      │ │ TP8 / EP8  │ │ TP8 / EP8  │ │ TP8 / EP8      │
              │ EAGLE 5/1/6    │ │ EAGLE 5/1/6│ │ EAGLE 5/1/6│ │ EAGLE 5/1/6    │
              │ CUDA graph 开  │ │            │ │            │ │                │
              │ ramdisk 权重   │ │            │ │            │ │                │
              │ :9002          │ │ :9002      │ │ :9002      │ │ :9002          │
              └────────────────┘ └────────────┘ └────────────┘ └────────────────┘
                     ▲                                                ▲
                     └──────── 同一智算中心内网 172.19.x.x ────────────┘
                        NAS 只读挂载 /root/gongji（权重源）
```

要点：

1. **Router 不带 `--pd-disaggregation`**，worker_type 全为 `regular`，只做负载均衡。
2. **Router 必须与副本同智算中心**（走内网 172.19.x.x），公网 hairpin 会导致 worker 长期 pending。
3. **四份副本彼此独立**：任一节点重启、升级、故障，不影响其余三份。
4. **每节点自带 ramdisk 权重副本**（306 GB），重启恢复 ≈ 1 分钟而非 13 分钟。

## 5. 单副本标准配置（4 台完全一致）

```bash
/opt/tai-talea/venv/bin/python -m sglang.launch_server \
  --model-path /dev/shm/GLM-5.3-Flash \
  --served-model-name zai-org/GLM-5.3-Flash \
  --chat-template /dev/shm/GLM-5.3-Flash/chat_template.jinja \
  --host 0.0.0.0 --port 9002 \
  --tp-size 8 --ep-size 8 \
  --kv-cache-dtype bfloat16 \
  --dsa-prefill-backend tilelang --dsa-decode-backend tilelang \
  --moe-runner-backend deep_gemm \
  --disable-custom-all-reduce \
  --disable-flashinfer-autotune \
  --speculative-algorithm EAGLE \
  --speculative-num-steps 5 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6 \
  --mem-fraction-static 0.60 \
  --context-length 32768 \
  --chunked-prefill-size 8192 --max-prefill-tokens 8192 \
  --max-running-requests 32 \
  --load-format runai_streamer \
  --model-loader-extra-config '{"concurrency":16}' \
  --reasoning-parser auto --tool-call-parser auto \
  --watchdog-timeout 1800 --dist-timeout 600
```

### 5.1 参数中不可动摇的项（改动会导致失败或显著退化）

| 参数 | 为什么不能动 |
| --- | --- |
| `--mem-fraction-static 0.60` | **0.70 必 OOM**（EAGLE draft-worker CUDA graph state init 显存不足），且 sglang 会把该 OOM 报成 `illegal memory access`——这正是 09-23 误判"MTP 不可用"的根因 |
| `--disable-flashinfer-autotune` | 社区点名的必需项 |
| `--kv-cache-dtype bfloat16` | Hopper 上 FP8 KV 与 TRT-LLM DSA 被禁用；TileLang DSA + FP8 KV 是非法组合 |
| `--disable-custom-all-reduce` | GLM-5.3-Flash 的 EP8 路径必需 |
| `--served-model-name` | **4 台必须完全一致**，否则 Router 视为 4 个不同模型，无法分流 |
| `--chat-template` 显式指定 | GLM-5.3-Flash 模板在**独立的 `chat_template.jinja`**，`tokenizer_config.json` 无内联模板。不显式指定则 warmup 报错、且 `auto` 解析器识别失败 |

### 5.2 预期生效状态（启动日志核对项）

- `speculative_algorithm = EAGLE`，`speculative_draft_model_path = None`（用 checkpoint 内置 MTP 头）
- decode CUDA graph：`backend: full`，`max_bs: 512`
- **prefill 段 CUDA graph 被自动禁用**（`Breakable CUDA graph is incompatible with KDA hybrid linear attention`）——**这是预期行为，不是配置错误**
- 每卡显存 ≈ 51.6 GB

## 6. 资源预算

### 6.1 显存

| 项 | 单节点 | 4 节点合计 |
| --- | --- | --- |
| GPU 总显存 | 8 × 80 = 640 GB | 2,560 GB |
| 权重（TP8 切分） | 37.98 GB/卡 = 304 GB | 约 1,224 GB（占 47.8%） |
| KV + CUDA graph | 13.6 GB/卡 ≈ 109 GB | 约 436 GB |
| 实际占用 | 51.6 GB/卡 ≈ 413 GB | 约 1,652 GB |

### 6.2 内存与存储

| 项 | 要求 |
| --- | --- |
| 每节点内存 | ≥ 512 GB（ramdisk 权重 306 GB + 页缓存/运行时）；实测节点为 2 TB，充裕 |
| 每节点 `/dev/shm` | ≥ 340 GB |
| NAS | 只读挂载 `/root/gongji`；4 节点合计需读取 4 × 306 GB ≈ 1.2 TB |
| 重启代价 | ramdisk 命中 ≈ 1 分钟；需重新拷贝 ≈ 13 分钟（@400 MB/s） |

按 8 卡规格 `PRD-CCI-5-208`（历史记录 20.48 B/时）估算，4 台合计 **≈ 81.9 B/时**。

## 7. 实施步骤

### 7.1 建议分两批上线（降低风险）

**第一批（3 副本）**：先起 3 台组成生产池，第 4 台作为金丝雀/备用。
**第二批（4 副本）**：第 4 台通过验收后并入 Router —— 追加 worker 只需改 Router 的 `--worker-urls` 并重启，无需停服（其余 3 台继续承接流量）。

### 7.2 步骤清单

| # | 步骤 | 关键动作 | 预计耗时 |
| --- | --- | --- | --- |
| P0 | 前置准备 | ① 确认 H100 8 卡库存与规格代码；② 扩展 Talea 参数白名单（见附录 A）；③ 把 `ninja`、tokenizer 文件、pip 源写进铺装清单 | — |
| P1 | 扩容 2 个新节点 | 经 CCI 创建 API 申请 2 × 8×H100，创建时声明 **NAS 只读挂载 `/root/gongji`**（挂载无法事后追加）；`autoReleaseTime` 设为长值或关闭，避免被平台静默释放 | — |
| P2 | 环境铺装 | Talea bootstrap 铺装：venv（`--system-site-packages`）→ `sglang` + `mooncake-transfer-engine` → `apt-get install -y ninja-build` → `/etc/pip.conf` 指 bfsu 主源 | ~12 分钟/节点，可并行 |
| P3 | 权重预热到 ramdisk | `cp -a /root/gongji/GLM-5.3-Flash /dev/shm/`，并**补齐 tokenizer 文件**（`tokenizer.json` / `tokenizer_config.json` / `chat_template.jinja` / `processor_config.json`） | ~13 分钟/节点；错峰或先验证 NAS 聚合带宽 |
| P4 | 启动 4 副本 | 统一 `glm-agg.sh` 启动；等待全部 `HEALTH_OK` | 4–6 分钟（含首次 JIT） |
| P5 | 启动 Router | 聚合模式，`--policy cache_aware`，注册 4 个 worker | < 1 分钟 |
| P6 | **预热压测** | 按目标并发档位（1/2/4/8/16/32）各打一轮，把每个 batch size 的 kernel 编译掉 | ~5 分钟 |
| P7 | 验收 | 按 §8 逐项验收 | — |
| P8 | 接入监控 | `--enable-metrics`，采集各副本吞吐/显存/健康状态与 Router worker 状态 | — |

### 7.3 Router 启动方式

```bash
/usr/local/bin/sgl-model-gateway launch \
  --host 0.0.0.0 --port 30000 \
  --control-plane-host 127.0.0.1 --control-plane-port 30001 \
  --worker-urls http://<n1>:9002 http://<n2>:9002 http://<n3>:9002 http://<n4>:9002 \
  --policy cache_aware
```

`cache_aware` 优于 `round_robin`：在多副本场景下能提高前缀缓存命中率（各副本系统提示词/工具定义高度重复时收益明显）。压测阶段可临时切回 `round_robin` 保证分流确定性。

## 8. 容量预测与验收标准

### 8.1 性能预测（以 2 节点实测曲线按每副本 bs 换算）

| 总并发 | 每副本 bs | 预测聚合吞吐 | 相对 2 节点 |
| --- | --- | --- | --- |
| 4 | 1 | ~744 tok/s | 2× |
| 8 | 2 | ~1,490 tok/s | 2× |
| 16 | 4 | ~2,490 tok/s | 1.23× |
| 32 | 8 | **~4,000–4,600 tok/s** | 2.0–2.3× |
| 64 | 16 | ~6,000–7,500 tok/s（待实测） | — |

单流延迟不随副本数变化：**186 tok/s / TTFT 0.15–0.19 s**。横向扩展买的是**并发吞吐**，不是单用户速度。

> 注：conc≥32 的档位在 2 节点上未测过（2 节点 conc=16 时每副本已是 bs=8，接近实测上限）。**该区间为外推值，必须经 P6 实测确认。**

### 8.2 验收清单

- [ ] 4 副本全部 `HEALTH_OK`，Router `/workers` 显示 4 个 `regular` worker 且 `is_healthy=true`、`model_id` 一致
- [ ] 单流 ≥ 180 tok/s，TTFT ≤ 0.25 s，accept length ≥ 2.5
- [ ] **热态** conc=16 ≥ 2,400 tok/s，conc=32 ≥ 4,000 tok/s
- [ ] 故障演练：`kill` 任一副本，Router 在 10 s 内摘除，其余 3 副本承接，无请求失败
- [ ] 连续压测 30 分钟：无 OOM、无 watchdog 超时、显存无增长
- [ ] 重启演练：单副本重启到恢复服务 ≤ 6 分钟

## 9. 风险与对策

| ID | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| **R1** | **平台是否仍有 8 卡 H100 可售**——历史记录显示可售列表只有 H800A（`PRD-CCI-5-201/202/204/208`） | 扩容受限；若改用 H800A，NVLink 带宽 400 GB/s vs 900 GB/s，TP8 all-reduce 与 EP8 all-to-all 会退化，186 tok/s 需重新标定 | **动手前先查 `list-for-cci` 库存**；若只有 H800A，先在 1 台上复跑基准再决定是否混合部署 |
| R2 | 冷编译悬崖：副本首次见到新 batch size 会现场 JIT，引擎停摆（实测 3.5 s → 15 s） | 首轮性能被严重低估，误判容量墙 | P6 强制预热；或按 sglang 提示做 serving 前预编译；监控区分首轮/复跑 |
| R3 | 缺 `ninja` | EAGLE + tilelang 的 JIT 编译直接崩 | 写进铺装清单，`apt-get install -y ninja-build` |
| R4 | ramdisk 副本缺 tokenizer 文件 | warmup 失败 + `auto` 解析器失效 | 写进铺装清单；P3 显式校验 4 个文件存在 |
| R5 | 副本 `model_id` 不一致 / Router 缓存旧值 | Router 视为多个模型，无法分流 | 统一 `--served-model-name`；改配置后**必须重启 Router** |
| R6 | Router 单点 | 整体不可用 | Router 与副本同 DC；准备第二个 Router 实例做热备（同 `--worker-urls`，前端切流） |
| R7 | NAS→ramdisk 带宽竞争 | 4 节点并行拷贝互相拖慢 | 错峰执行，或先测 NAS 聚合带宽；必要时串行 4 × 13 分钟 |
| R8 | ramdisk 属易失存储 | 节点重启后权重丢失，恢复需 13 分钟 | 接受（ramdisk 命中时重启仅 1 分钟）；长期可用 `save-image` 固化镜像 |
| R9 | Talea 白名单未覆盖新参数 | 配置下发被 400 拒绝 | 按附录 A 扩容 `ALLOWED_EXTRA_FLAGS` |
| R10 | `autoReleaseTime` 过期静默释放 | 实例被平台回收，服务中断 | 创建时关闭自动释放或设置足够长的到期时间 |
| R11 | `--context-length 32768` + `--max-running-requests 32` 的 KV 上限 | 长上下文或高并发时可能 KV 不足 | 如需 128K/更大并发，需重新做显存分配实测；必要时降低并发或提高 `mem-fraction-static`（但不得回到 0.70） |

## 10. 运维要点

1. **扩缩容**：加副本 = 起新副本 + 改 Router `--worker-urls` 重启（秒级，其余副本继续服务）；减副本 = 先摘流（readiness）再停服务。
2. **摘流而非删除**：RouterAdapter 刻意不提供 `DELETE /workers`，摘流走 readiness——这是设计约束，运维脚本不要绕过。
3. **镜像固化**：环境（venv + ninja + pip 源）验证通过后建议 `save-image` 固化，把 P2 从 12 分钟压到接近 0。
4. **版本一致性**：4 副本必须使用同一 sglang 版本与同一份权重。注意当前容器装的是**公共版 sglang 0.5.20**，内部 fork 的适配尚未落地——本方案基于公共版验证结果。
5. **监控项**：各副本 `accept len`（投机有效性）、`#running-req`、显存、`Decode batch` 吞吐；Router 的 worker 健康与分流分布。
